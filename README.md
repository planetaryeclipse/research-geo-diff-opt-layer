# Supplementary Code Submission

This directory contains the supplementary code for the IEEE ITSC conference submission titled "Differentiable Manifold Optimization Layers for Learned Safety-Critical Geometric Controllers". Please read the following instructions for setting up the repository and how to run the individual files (and make adjustments if necessary).

> Please note that the following instructions have been tested on a system running `Ubuntu 24.04`. If running on a different flavor of version of Ubuntu then it is likely the instructions may still work but may need modifications. This demo code was not designed with Windows in mind.

The following outlines the folder structure of this directory:

- `diff_mfld_optim` contains a custom implementation of a differentiable geometry library with autograd capabilities so we can change custom metrics without having to manually define all the Christoffel symbols. Note that this is setup as an editable library in the `requirements.txt` file so restarting scripts utilizing this library will use the current version of the files.
- `experimentation` contains various testing files that were used for both the controller and any necessary derivations
  - `unicycle_cntrllrs` contains the testing notebooks for the dynamic unicycle controller. Note that originally a control lyapunov function (CLF) based controller was used but was found to cause too many erratic motions. This thereby necessitated the use of the controller developed in `dyn_ext_unicycle_mpc.ipynb` which was folded into the scripts used to generate the training data for the networks
  - `unicycle_derivs` contains the notebooks used to derive the GHOCBF constraint to use in the GHOCBF-QP problem. It also contains the derivations for the optimization problem for the vestigial CLF controller as well.
- `geo_diff_opt_layer_ml` the main repositiory for hosting the training data, training scripts, and traiing results.
  - `data` contains the generated training data
    - `episodes` contains the generated trajectories and the starting point associated with each. Data in this folder is generated by the notebook `util/trajectory_generation.ipynb`
    - `nominal_mpc` contains the state poositions and generated control by the expert (MPC-based) controller for each episode. Data in this folder is generated by the notebook `util/nominal_mpc_generation.ipynb`
    - `keep_out` generates the random keep-out circles (with center/radius velocity/acceleration). Data in this folder is generated by the notbook `util/ko_cbf_generation.ipynb`
  - `training` contains the training results and the Python scripts required to run the training
    - `geo_results` the folder directories where occasional intermediate generated network parameters and batch histories are generated to. Note that if restarting then the batch history generated after the restart and before the crash will be separate (needs to be combbined afterwards) but this is not a concern if running the whole training procedure from scratch.
      - `euclid` contains the training results from running the `cvxpy`-based results from script `train_nn_cvxpy_script.py`
      - `nonprod_flat_metric` contains the training results from running the differentiable manifold optimization layer with the Euclidean metric from script `train_nn_nonprod_gcbf_script.py`
      - `nonprod_nonflat_metric` contains the training results from running the differentiable manifold optimziation layer with the non-Euclidean metric from script `train_nn_nonprod_gcbf_nonflat_metric_script.py`
    - `controller.py` helper class containing the controller model description. Note that there is an internal parameter that can be set to allow it to accept and `h` and `h_grad` to allow the controller to learn how to avoid an obstacle but these are *disabled* during testing so the controllers presented in the results are entirely trained on the expert controller through the optimization layer so the model itself has no knowledge of the constraint
    - `euclid_cbf.py` contains helper functions for implementing the Euclidean formulation within `cvxpy`
    - `gcbf_nonprod.py` contains helper functions for implementing the geometric HOCBF formulation with the differentiable manifold optimization layer
    - `train_nn_cvxpy_script.py` is the script for the training under the differentiable convex optimization layer implemented using `cvxpylayers`
    - `train_nn_nonprod_gcbf_script.py` is the script for the training under the differentiable manifold optimization layer implemented with the Euclidean metric
    - `train_nn_nonprod_gcbf_nonflat_metric_script.py` is the script for the training under the differentiable manifold optimization layer implemented with the non-Euclidean metric
    > Note that the training files are *not* provided as IPython notebooks as training was setup to be run on multiple systems for performance reasons during testing. For the final data found in the current version of this directory before running any scripts, the data was run on a single system. However, the Python scripts are segmented by sections using %% so it is possible to run invidiual cells in VS Code. However, running in this way will not provide the boost from using free-threading Python so please follow the alternative instructions we've indicated here.
    - `traiing_comparison_results.ipynb` is the notebook that can be used to generate the figures comparing results.
      - Unfortunately, given the specification of timestamps, it will be necessary to select the filenames individually when loading into the dictionary. Once done, then the `batch_num` property will have to be manually adjusted based on how many batches you wish to present. Then you will need to index each set accordingly in the dictionary noting that each loaded file ended after the batch number specified in its filename so it has `batch+1` data points.
      > Note that if you terminate training of all 3 scripts after the 50 epochs backup data has been generated then you do not need to make any adjustments to the indexing.

## Running Training

Please follow the setup steps (below this section) if you have not already done so.

### Euclidean (`cvxpylayers`) Training

1. Switch to run the `.ipython_venv` virtual environment to use Python 3.12
2. On the command line, navigate to `training` using `cd geo_dif_opt_layer_ml/training/`
3. Run training via `python3 train_nn_cvxpy_script.py`. Terminate after the epoch 50 data generates (or wait until completion).

> Note that we have to be in this folder as it will generate the output files into `geo_results/euclid` which is specified relative to this directory.

### Training Under Euclidean Metric

1. Modify the `num_processes` variable in `train_nn_nonprod_gcbf_script.py` to the amount of cores you want to run the process with
2. Switch to run the `.venv` virtual environment to use free-threading Python 3.14
3. On the command line, navigate to `training` using `cd geo_dif_opt_layer_ml/training/`
4. Run training via `PYTHON_GIL=0 python3 train_nn_nonprod_gcbf_script.py` as this will force the use of disabling the GIL which allows us to accelerate batch processing. Terminate after the epoch 50 data generates (or wait until completion).

### Training Under Non-Euclidean Metric

1. Modify the `num_processes` variable in `train_nn_nonprod_gcbf_nonflat_metric_script.py` to the amount of cores you want to run the process with
2. Switch to run the `.venv` virtual environment to use free-threading Python 3.14
3. On the command line, navigate to `training` using `cd geo_dif_opt_layer_ml/training/`
4. Run training via `PYTHON_GIL=0 python3 train_nn_nonprod_gcbf_nonflat_metric_script.py` as this will force the use of disabling the GIL which allows us to accelerate batch processing. Terminate after the epoch 50 data generates (or wait until completion).

> If you want to experiment with different metrics, modify the `metric_field` variable accordingly. Currently it is set to the following where `u_f` and `u_t` are `u_1` and `u_2`. Note that you do *not* need to change any Christoffel symbols as this will be computed automatically.

```python
metric_field = MetricField(
    lambda u_f, u_t: torch.tensor(
        [[0.5 * u_f**2 + 1.0, 0.0], [0.0, 0.5 * u_f**2 * 0.5 * u_t**2 + 1.0]]
    )
)
```

> Note that due to current limitations of the current manifold solver, substantial changes to this metric may lead to issues with convergence problems in the forward pass. The current solver configurations are listed below but reducing this computational cost (sometimes given high iterations necessary) and increasing robustness is slated for future work.

The authors have found that the following works well for the current non-Euclidean metric. If you modify the metric it is advised that you attempt to increase `penalty_growth` slowly and potentially decrease `subsolver_acc_growth` in alternating steps to try and force convergence faster in the earlier iterations of the subsolver method.

```python
# optimization params (note the large lagrange multiplier limits given the use
# of the higher order control barrier functions)

constr_solv_cfg.penalty = 1.0  # must be greater than 1 to grow
constr_solv_cfg.penalty_growth = 1.2  # must be greater than 1
constr_solv_cfg.ratio = 0.8
constr_solv_cfg.max_iters = 1000
constr_solv_cfg.conv_eps = 1e-2  # this is ignored by constrained solver control

constr_solv_max_mult = torch.inf  # 1_000_000.0
constr_solv_cfg.g_mult_clips = (-constr_solv_max_mult, constr_solv_max_mult)
constr_solv_cfg.h_mult_clips = (-constr_solv_max_mult, constr_solv_max_mult)

subsolver_cfg.damp = 0.1
subsolver_cfg.damp_growth = 0.95
subsolver_cfg.max_iters = 5000  # needed due to earlier training error
subsolver_cfg.damp_clip = [1e-4, 1.0]

constr_solv_cfg.subsolver_acc_min = 1e-4
constr_solv_cfg.subsolver_acc = 1e-3  # starting
constr_solv_cfg.subsolver_acc_growth = 0.85
```

## Setup Instructions

### Install Free-Threading Python 3.14

Unfortunately as this is testing code the differentiable geometric optimization layers are written in pure Python and is slow as a result. Using process-based `multiprocessing` is not possible due to an error with the way some `torch` objects are serialized so we have to use regular threading. Therefore to get a large speedup we need a version of Python released from the global-interpreter-lock (GIL).

Please follow the following instructions to install free-threading Python 3.14.

```bash
sudo add-apt-repository ppa:deadsnakes
sudo apt-get update
sudo apt-get install python3.14-nogil python3.14 python3.14-dev
```

Now we need to setup the virtual environment with this free-threading build.

```bash
sudo apt install python3.14-venv

python3.14-nogil -m venv .venv
source .venv/bin/activate
pip3 install -r requirements.txt # install all sys requirements
```

Check that the environment is setup properly.

```python
import sys
sys._is_gil_enabled()  # should be False
```

### Install Python 3.12 for IPython and CVXPY

For whatever reason, this version of Python fails to work with `cvxpy` and is incoimpatible with `ipython` notebooks when opened with VS Code. Therefore we will also install Python 3.12 with a second version of Python.

```bash
deactivate # disable to the current workspace
sudo apt-get update
sudo apt-get install python3.12 python3.12-dev python3.12-venv
```

Then setup the new virtual environment, which we'll call `.ipython-venv` as opposed to the original `.venv`, using the following.

```bash
python3.12 -m venv .ipython_venv
source .ipython_venv/bin/activate
pip3 install -r requirements.txt
```
